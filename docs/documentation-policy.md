# 文書管理方針

この文書は、正本文書の責務、配置、更新、統合・廃止の判断基準を定めます。

## 正本文書全体の責務

| 文書 | 担当 | 更新する場面・境界 |
| --- | --- | --- |
| [README](../README.md) | 概要、最短の開始手順、目的別の文書案内 | 開始方法や参照先が変わるとき。詳細な操作・仕様・現在地を抱えない |
| [AGENTS](../AGENTS.md) | 作業者の行動規約、変更・検証・承認の原則 | 作業規約が変わるとき。機能仕様や直近の記録を蓄積しない |
| [brief](brief.md) | 目的、利用者、対象・非目標、方向性を規定する選択、成功の判断 | プロジェクトの方向性を変える合意があったとき |
| [roadmap](roadmap.md) | 今後到達したい状態、着手・再検討条件、依存・優先関係 | 目標や条件が変わるとき。達成した目標は現役の項目から外す |
| [利用ガイド](user/guide.md) | 環境準備、基本用語、日常フロー、操作の選び方、共通設定 | 利用方法が変わるとき。CLIや画面の詳細は各ガイドへ |
| [CLIガイド](user/cli.md) | 公開commandの入力・出力・副作用・使い方 | 公開CLI契約が変わるとき。内部の判定規則は仕様へ |
| [Web UIガイド](user/web-ui.md) | 起動・自動起動、画面、操作、利用者から見たjobとアクセス境界 | Webの利用方法が変わるとき。内部API・worker契約は仕様へ |
| [architecture](developer/architecture.md) | moduleの責務・依存方向・主要処理の接続 | 実装の構成や接続が変わるとき。個別機能の詳細は仕様へ |
| [status](developer/status.md) | 機能・運用上の関心事ごとに、現在頼ってよい範囲 | 接続・適用・制約・確認範囲が変わった項目を置き換える |
| `developer/specs/` | 機能・データ・判断の契約 | 対象の意味、入力、出力、規則、保証が変わるとき |
| `developer/workflows/` | 開発・検証・評価の手順 | 作業の実施条件・確認方法が変わるとき。確認範囲はstatus、完了した実行結果の詳細はGitへ |

`docs/`直下はプロジェクト全体の目的・目標・統治に使います。`docs/developer/`には開発・保守・運用の判断に使う文書を置き、architectureとstatusは実装全体の構成と現在の適用・確認範囲を扱います。`docs/notes/`には、検討途中の具体的な問いと有効な保留・再開材料を、判断・作業に必要な間だけ置きます。

## 文書を分ける単位

読者が答えを得たい問いと、一緒に理解・変更・保守すべき内容を単位にします。moduleやcommandごとの機械的な分割、文章量だけを理由にした分割はしません。同じ判断の原則・現行規則・必要な設計理由は近くに置きます。

さらに分けるのは、別の目的で参照され、それぞれ単独で理解でき、変更時に一緒に見直す必要が少なく、定義や条件の再掲を増やさない場合です。複数文書が同じ目的のまとまりになったらsubdirectoryを設けます。全領域の階層を揃える必要はありません。統合する場合も、対象や前提が違う判断を同じ規則へまとめません。

同じ話題への言及は禁止しません。たとえば中断について、Webガイドは操作・表示、job仕様は処理契約、statusは接続・確認範囲を説明します。同じ詳細な条件を複数箇所で独立管理せず、担当正本へ参照します。

## 概要と参照の置き方

本文は意味のまとまりで段落を分け、一つの段落を一行で書きます。表示幅に応じた折り返しは閲覧側に任せます。箇条書きの項目内も同様とし、コードブロック・表など構造上必要な改行は保持します。

冒頭では対象と全体像を説明します。機能の仕様なら、入力から何を得るか、主な判断や処理がどうつながるかを示します。field・enum・例外条件・moduleの一覧は、その後に必要な箇所を選んで読める順序と見出しにします。概要は関係の理解に、詳細は条件や値の確認に使えるように書き分けます。

文書の担当分担と一般的な更新ルールはこの方針に集約します。各文書では、合意済みの設計と現行規則の違い、観測と採用の違いなど、内容を理解するために必要な境界を該当箇所で説明します。

リンクは、読む文書の選択、判断に必要な契約、根拠となる記録へ案内するために置きます。参照先で何を確認できるかを本文から分かるようにし、説明や導線が重複するリンクは整理します。

文書は可能な限りHEADだけで完結するようにします。必要な説明・比較材料は現在の本文や管理対象fileへ置き、別taskの文書、旧worktree、一時file、過去commitを読むことを前提にしません。必要な外部URLや実行条件としてのrevisionの記録は使えます。

## 全体文書の更新方法

### Brief

目的・対象・非目標と、それを規定する選択、提供したい価値を記します。個人ローカル運用や紹介可否の最終判断者など、プロジェクトの方向性を変える合意があったときに更新します。

### Status

機能・運用上の関心事ごとに、何をすると何が得られるか、通常導線・実運用で使われているか、利用判断に影響する制約は何かを示します。実装あり、通常接続、実運用適用を区別し、根拠となる確認範囲と時点を添えます。

接続・適用・制約が変わったら、該当項目を現在の説明に置き換えます。どの場面で役立つかと、確認できた範囲・限界を短くまとめます。再利用する確認方法はworkflowへ、特定作業の再開に必要な条件はnotesへ分けます。過去の実行日や件数は、現在の利用判断に必要な場合だけ記します。

### Roadmap

各項目は、解消したい問題、到達したい状態、達成の判断を中心にし、必要な着手条件・依存・優先関係を添えます。解法の候補は検討中であることを明記します。部分達成したら残る目標に書き直し、達成した目標は現役の項目から外します。

## 現行仕様・設計・記録

- 現行仕様はコード・通常経路と照合し、代替・shadow経路は適用範囲を明示する。
- 合意済みで未実現の設計は、現行規則と区別して示す。到達目標・着手条件はroadmapへ記す。
- 現在の設計を支える理由・反例は仕様へ、現在の説明を支える検証範囲と限界はstatusへ置く。
- 未決の選択肢、比較途中の材料、判断できなかった具体例は、何が未決か、何を確認すれば進めるか、どの条件で再検討するかを添えてnotesに置く。観測時点と現在の状態を区別する。
- notesの内容が確定したら、現在のコード・合意・適用記録と照合し、必要な情報だけ担当正本へ反映して重複を削る。
- 完了した作業の経緯、試行結果、適用記録は、特記すべき事情がない限り現役文書から削除する。Gitに履歴が残ることを前提とし、各文書に過去の記録を探す案内を付けない。過去の判断を読む必要がある場合だけ、目的とcommit hash・対象pathを示す。文書全体のarchiveや廃止文書への転送stubは作らない。
- 未実装・未検証の項目は現在の目標との関係を確認し、継続する理由があるものをroadmapまたは保留として残す。凍結・保留中の作業は、完了記録と区別して扱う。

特定作業の再開に必要なrun ID、保留指示、backup・archiveの注意は、その作業のnotesに置きます。有効な保留・注意はstatusから参照し、解消したら本文と導線から外します。恒久的な注意は規約・手順へ反映します。文書の削除と、そこで参照していた運用データ・backup・恒久archiveの削除は別の判断です。

## 暫定的な独立機能

独自の目的・データ・実行経路を持ち、本体との接続が限定されている機能は、一つの独立した仕様にまとめます。暫定機能も、実装済みの契約は仕様として扱います。収集・保存・評価を横断する場合も、機能を一通り理解できるまとまりを優先します。

仕様の冒頭に独立させている理由、現在の用途、本体との入力・出力・変更権限の境界を示します。継続・統合・停止の判断に必要な観測と条件を明確にし、実装された検出条件は仕様、判断待ちの目標はroadmap、確認範囲はstatusへ記します。未決の判断に必要な観測材料だけをnotesに保持します。

本体へ統合したら契約も各担当正本へ移します。停止・撤去した機能の仕様は現役文書から外し、必要な経緯を履歴へ残します。独立して継続する場合は、その目的と接続範囲に合った文書構成を維持します。

## 移動・統合時の確認

内容の正本と必要な参照を新しい配置へ揃え、本文を持たなくなった節は削除します。文書を廃止する場合は、有効な指示や未完了作業の参照先を確保します。見出しへのlinkと、command・コードとの整合性を確認します。

参照更新だけが目的の文書では、本文の内容を保持します。

## 利用者向け用語の編集

README、brief、利用者向け文書は、操作や判断を理解できる日本語を優先し、意味と呼称は[利用ガイドの基本用語](user/guide.md#基本用語)を正本とします。コマンド名、オプション、JSON field、enumはバッククォート付きで原名を示します。画面の操作手順には実際の日本語ラベルを用います。開発文書ではコード検索と実装上の区別を優先し、内部用語を無理に訳しません。

- 一般的な外部projectとDBの登録プロジェクトを区別する。開発文書ではproject row、dict、table等の形も維持する。
- `run`は調査実行記録、一括実行、収集処理、background jobで単位が異なるため対象を添える。
- `confirmed`は自動判定にも使われ、利用者操作の「採用」と完全な同義語にはしない。`classification`もidentifier、relation、evidenceのどれかを明示する。
- `review`はqueue、signal、target、job、一般的な確認行為を一括置換しない。利用者向け機能名は「要レビュー一覧」「紹介候補一覧」とし、後者を「昇格候補」とは呼ばない。
- `sync`は双方向同期を意味せず、dry-runは「取り込み候補の確認」と説明する。`merge`は登録プロジェクトのマージに使い、調査根拠のintegrationには使わない。
- `source`、`surface`、`family`、`current`、`bounded`、`guard`等は固定訳を増やさず、文脈に応じて具体的に説明する。

Web UIは日本語を基本とし、JSON等の馴染みのある技術ラベルは原表記も使います。内部のAPI・DB値とは表示層で分離し、原文引用、利用者の入力、URL、識別子、製品・プロトコルの固有名詞、JSONや診断記録は改変しません。未認識の診断を推測で翻訳せず、日本語の案内に技術詳細を添えます。多言語切替は設けません。画面の改名時は関連する利用手順を同期します。

操作画面では、現在の状態、判断材料、操作の効果を見通せることを優先します。説明は必要になる操作の近くへ置き、常設する必要がなければ削ります。補足を開く場合は内容を予想できる名前にし、説明と設定を区別します。キーボードとタッチでも到達できるようにし、重要な警告をhoverだけに隠しません。コマンドやJSON等の読み飛ばしやすい情報を面積だけの理由で隠さず、文字縮小より先に重複・余白・配置・強調を整理します。ボタンは自然な動作名にし、複数の意味を「・」で詰め込みません。
