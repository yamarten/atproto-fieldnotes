# 文書管理方針

この文書は、正本文書の責務、配置、更新、統合・廃止の判断基準を定めます。
READMEは読む目的に応じた入口、AGENTSは作業時の規約を担当し、詳細な責務表はここだけで管理します。

## 正本文書全体の責務

| 文書 | 担当 | 更新する場面・境界 |
| --- | --- | --- |
| [README](../README.md) | 概要、最短の開始手順、目的別の文書案内 | 開始方法や参照先が変わるとき。詳細な操作・仕様・現在地を抱えない |
| [AGENTS](../AGENTS.md) | 作業者の行動規約、変更・検証・承認の原則 | 作業規約が変わるとき。機能仕様や直近の記録を蓄積しない |
| [brief](brief.md) | 目的、利用者、対象・非目標、方向性を規定する選択、成功の判断 | プロジェクトの方向性を変える合意があったとき |
| [status](status.md) | 機能・運用上の関心事ごとに、現在頼ってよい範囲 | 接続・適用・制約・確認範囲が変わった項目を置き換える |
| [roadmap](roadmap.md) | 今後到達したい状態、着手・再検討条件、依存・優先関係 | 目標や条件が変わるとき。達成した目標は現役の項目から外す |
| [利用ガイド](user/guide.md) | 環境準備、基本用語、日常フロー、操作の選び方、共通設定 | 利用方法が変わるとき。CLIや画面の詳細は各ガイドへ |
| [CLIガイド](user/cli.md) | 公開commandの入力・出力・副作用・使い方 | 公開CLI契約が変わるとき。内部の判定規則は仕様へ |
| [Web UIガイド](user/web-ui.md) | 起動・自動起動、画面、操作、利用者から見たjobとアクセス境界 | Webの利用方法が変わるとき。内部API・worker契約は仕様へ |
| [architecture](developer/architecture.md) | moduleの責務・依存方向・主要処理の接続 | 実装の構成や接続が変わるとき。個別機能の詳細は仕様へ |
| `developer/specs/` | 機能・データ・判断の契約 | 対象の意味、入力、出力、規則、保証が変わるとき |
| `developer/workflows/` | 開発・検証・評価の手順 | 作業の実施条件・確認方法が変わるとき。実行結果は記録へ |

`docs/`直下はプロジェクト全体の目的・現在地・目標・統治に使います。開発フェーズや一時的な作業単位を
理由に文書を増やしません。`docs/notes/`は検討・比較・履歴・作業固有の再開情報の置き場で、現行仕様の正本ではありません。

開発・検証の手順は[変更の受入](developer/workflows/change-acceptance.md)と
[LLM model評価](developer/workflows/llm-model-evaluation.md)を正本にします。
通常調査でLLMに何を任せるかと、LLM構成を変更する際に何を比較するかを分けます。

## 文書を分ける単位

読者が答えを得たい問いと、一緒に理解・変更・保守すべき内容を単位にします。
moduleやcommandごとの機械的な分割、文章量だけを理由にした分割はしません。
同じ判断の原則・現行規則・必要な設計理由は近くに置きます。

さらに分けるのは、別の目的で参照され、それぞれ単独で理解でき、変更時に一緒に見直す必要が少なく、
定義や条件の再掲を増やさない場合です。複数文書が同じ目的のまとまりになったらsubdirectoryを設けます。
全領域の階層を揃える必要はありません。統合する場合も、対象や前提が違う判断を同じ規則へまとめません。

同じ話題への言及は禁止しません。たとえば中断について、Webガイドは操作・表示、job仕様は処理契約、
statusは接続・確認範囲を説明します。同じ詳細な条件を複数箇所で独立管理せず、担当正本へ参照します。

## 概要と参照の置き方

各文書は、何を扱い、どの入力から何を得るか、主な判断や処理がどうつながるかを冒頭で説明します。
field・enum・例外条件・moduleの一覧は、その全体像を理解した後に必要な箇所を読める順序と見出しにします。
概要では関係を説明し、詳細の条件や値をもう一組保守する要約表にはしません。

リンクは、入口で読む文書を選ぶ場合、別の契約が判断に必要な場合、根拠となる記録を確認する場合に置きます。
移動したという理由だけで、元の場所に参照だけの節を残しません。内容を持たなくなった節は削除し、必要な
参照元を新しい正本へ直接つなぎます。同じ文書内の近接する節、仕様一覧、status・roadmapへの案内を機械的に
繰り返さず、リンクを外しても説明が成立する場所では省きます。

## 全体文書の更新方法

### Brief

「主要な判断」は、個人ローカル運用や紹介可否の最終判断者など、目的・対象・非目標を規定する選択です。
「成功の判断」は、どんな価値を提供できれば目的を果たしたといえるかです。
個別の実装方式、heuristic、testの受入条件、作業中の判断で頻繁に更新しません。

### Status

機能・運用上の関心事ごとに、何をすると何が得られるか、通常導線・実運用で使われているか、
利用判断に影響する制約は何かを示します。実装あり、通常接続、実運用適用を区別します。
保存済みの適用記録から分かることを、現在の実環境を再確認した結果として書きません。

検証は、その説明を支える根拠と限界を短く添えます。たとえば保存・replayを確認できても定期運用が未確認なら、
その境界を明記します。実行日、test件数、修正内容を作業ごとに追記せず、同じ項目の現在の説明を置き換えます。
詳細は検証記録へリンクし、過去の件数・旧制約・変更一覧を現在の機能説明に蓄積しません。

### Roadmap

各項目は、解消したい問題、到達したい状態、達成の判断を中心にし、必要な着手条件・依存・優先関係を添えます。
検討中の解法を実装要件へ昇格させません。「ここまでできた」を追記せず、部分達成で残る目標が変われば項目を
書き直し、達成した目標は外します。現在値と検証結果はstatus、詳細な比較・検討はnotesへ置きます。

## 現行仕様・設計・記録

- 現行仕様はコード・通常経路と照合し、実装済みの代替・shadow経路を通常経路と区別する。
- 合意済みでも未実現の設計は、現行規則と明確に分ける。実現する目標・着手条件はroadmapへ参照する。
- 検討中の仮説、比較結果、詳細な検証・適用記録はnotesに置き、状態と確認時点を明記する。
- notesだけに確定事項を残さず、コード・合意・適用記録を照合したうえで担当正本へ反映する。
  記録当時の仕様を現在の仕様と推定しない。

常設のthread-handoffは持ちません。現在地はstatus、目標はroadmap、恒久的な注意は規約・手順へ集約します。
特定作業の再開にだけ必要なrun ID、保留指示、backup・archiveの注意は、その作業のnotesに置きます。
有効な保留・注意がある間はstatusから参照できるようにし、解消したら現在地の導線から外します。
文書廃止時も、有効な指示・未完了作業の参照先を確保してから旧文書を削除します。

## 暫定的な独立機能

独自の目的・データ・実行経路を持ち、本体との接続が限定されている間は、一つの独立した仕様にまとめます。
暫定という理由だけで実装済み契約をnotesへ置きません。収集・保存・評価を横断して一つの機能を理解する必要が
ある場合は、分類を揃えるために文書を分散させません。

仕様の冒頭に独立させている理由、現在の用途、本体との入力・出力・変更権限の境界を示します。
見直しに必要な観測と、継続・統合・停止を判断する条件を明確にします。実装された検出条件は仕様、
判断待ちの目標はroadmap、実際の観測結果は記録を担当とします。

本体へ統合したら契約も各担当正本へ移します。停止・撤去した機能を現行仕様として残さず、必要な経緯を履歴へ
残します。成熟度だけによる`experimental/`等の分類は設けず、独立したまま継続する機能も同じ基準で扱います。

## 移動・統合時の確認

内容の正本、参照先、見出しへのlink、command・コードとの整合性を確認します。
利用者向けの基本用語は[利用ガイド](user/guide.md#基本用語)、編集上の境界は
[用語メモ](notes/user-facing-terminology.md)を参照します。開発文書のコード・DB・enum対応語を一括翻訳しません。
参照更新だけが目的の文書では、操作手順や履歴本文を併せて書き換えません。
