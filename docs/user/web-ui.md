# Project Registry Web UIガイド

`project-registry-web`はschema version 5のSQLite DBを操作する、1人の利用者向けのローカルWeb UIです。日常的な登録、調査、候補整理、登録プロジェクトの修正はWeb UIを主導線とし、低水準の監査や保守は[CLIガイド](cli.md)へ分けています。基本用語は[利用ガイド](guide.md#基本用語)を参照してください。

画面の操作・説明・状態は日本語で表示します。プロジェクト名、引用、URL、NSID、OAuth scopeの原文、JSON、システム履歴・外部エラーの技術詳細は原表記を保ちます。

## 起動

Web UIへのログインには、自分で設定したトークンを使います。アカウント登録は不要で、起動時に指定した値をブラウザーの初回入力ダイアログへ入力します。この値を知る人はDBの閲覧・編集や調査の実行ができるため、秘密の値として扱います。

```bash
export ATPROTO_SURVEY_WEB_TOKEN='your-web-login-token'
project-registry-web --host 127.0.0.1 --port 8765
```

| オプション | 意味 |
| --- | --- |
| `--host` | 接続を待ち受けるアドレス。既定は同じ端末からだけ接続できるループバックアドレス。 |
| `--port` | ポート。既定は`8765`。 |
| `--db-path` | 接続するSQLite DB。既定は`data/survey.db`。 |
| `--token` | Web UIのログインとAPI認証に使うトークン。`ATPROTO_SURVEY_WEB_TOKEN`でも指定できる。 |
| `--reload` | Web実装変更時にサーバープロセスを再起動する。 |
| `--reload-interval` | reload確認間隔。 |

CLI/Webの手動確認用DBは、先にCLIで架空データから生成します。

```bash
project-registry dev-db
project-registry-web --host 127.0.0.1 --port 8765 --db-path data/dev/survey.db --token web-ui-dev
```

このDBは繰り返し使えます。初期状態へ戻すときはWebとworkerを停止して`project-registry dev-db --reset`を実行します。代表データと安全境界は[共通ダミーDBの手順](../developer/workflows/change-acceptance.md#cliwebの共通ダミーdb)を参照してください。空の別DBが必要なら`project-registry init-db --db-path PATH`で初期化します。

### macOSでの自動起動

`project-registry-web-service`は、現在のcheckoutを参照する利用者用LaunchAgentを`~/Library/LaunchAgents/`へ生成します。ログイン時に実運用設定の`0.0.0.0:8888`で起動し、異常終了時は30秒以上の間隔を置いて再起動します。同じMacからの状態確認と管理には`http://127.0.0.1:8888/`を使います。Web serverが起動するworkerと定期実行も同じprocess環境を引き継ぎます。

導入前に`direnv`をinstall・allowし、`.envrc`へ`ATPROTO_SURVEY_WEB_TOKEN`と必要なLLM設定を置きます。LaunchAgentは対話shellを読まないため、`direnv exec`経由でこの環境を読みます。秘密を含む`.envrc`は他の利用者から読めないpermissionにしてください。

```bash
chmod 600 .envrc
project-registry-web-service install
project-registry-web-service status
```

| コマンド | 動作 |
| --- | --- |
| `project-registry-web-service install` | plistを生成または置換して起動。正本DBの存在とschema、direnv、tokenを事前確認 |
| `project-registry-web-service status` | launchdのload・process状態、bind先とloopbackからの応答を表示 |
| `project-registry-web-service restart` | 認証済みreload APIでworkerを停止してから同じ引数で再起動 |
| `project-registry-web-service uninstall` | processを停止してplistを削除。エラーログは保持 |

plistにはtokenやAPI keyを保存しません。token入り起動URLが出る標準出力は保存せず、例外等の標準エラーだけを`~/Library/Logs/atproto-survey/project-registry-web.err.log`へ保存します。同じMacでは`http://127.0.0.1:8888/`、LAN内の別端末ではMacの管理下のaddressを開き、初回の`Project RegistryのAPIトークン`入力ダイアログへtokenを入力します。tokenはoriginごとにbrowserのlocalStorageへ保存されます。

LaunchAgentはcheckoutとDBを絶対パスで参照します。リポジトリを移動した場合は旧checkoutで`uninstall`してから新しい場所で`install`し直してください。通常起動には`--reload`を付けません。コード更新後は設定の`サーバーを再起動`または`project-registry-web-service restart`を使います。

### Python環境の切替

通常reloadと`project-registry-web-service restart`は起動中のPython世代を維持します。Python更新には[候補環境の準備・検証](python-environment.md)後に、LaunchAgentの停止と新規起動が必要です。installはdirenv内のPython環境も事前確認し、壊れた環境なら既存serviceの停止前に拒否します。

実運用への適用承認後、実行中job・worker・CLIがないことを確認します。ジョブ一覧とeventは停止時に失われるため、必要な結果を先に確認します。`.envrc`に候補検証用の`PROJECT_REGISTRY_PYTHON_ENV`を残しません。

```bash
unset PROJECT_REGISTRY_PYTHON_ENV
# 初回移行でも旧Homebrew環境を使わず、候補Pythonから停止する
PROJECT_REGISTRY_PYTHON_ENV="$PWD/.runtime/candidate/venv" project-registry-web-service uninstall
# 初回移行で.venvが実directoryの場合だけ、停止後に退避
# mv .venv .venv-legacy
project-registry-python-env activate candidate
project-registry-python-env status
project-registry-web-service install
project-registry-web-service status
```

新規起動後に画面・静的asset・認証付き設定/一覧/job APIをHTTPと運用中のHTTPS入口で確認します。設定APIの`build.python_executable`と`build.python_base_prefix`を候補世代の実pathと照合します。確認用serverやtokenで本番を置き換えません。LaunchAgentのlabel、bind、port、DB、Tailscale設定は変わりません。

失敗時は新serviceを停止し、旧専用世代をactivateしてinstallし直します。利用できる旧専用世代がない場合は、[切替と復旧](python-environment.md#切替と復旧)に従って専用環境を再準備します。検証用worktreeから本家への世代コピーはできず、本家で再準備します。実際に適用するまで本番のPythonが独立管理へ移ったとは扱いません。

### Tailscale経由のHTTPS

Tailscale Serveを設定すると、tailnet内のHTTPS入口から同じWeb UIとDBを利用できます。接続端末でTailscaleを有効にし、対象Macへの接続が許可されたtailnetから開きます。入口のURLは`tailscale serve status`で確認します。Tailscale ServeがTLSを終端し、同じMacの`http://127.0.0.1:8888`へ転送します。Funnelによる一般公開は行いません。

初回は`Project RegistryのAPIトークン`入力ダイアログに、実運用checkoutの`.envrc`で設定している同じAPI tokenを入力します。HTTPとHTTPSは別originなので、tokenと一覧件数などのUI設定は引き継がれません。tokenをURLへ付ける必要はありません。再入力する場合は設定の`APIトークンを削除`で削除してページを再読込します。

設定の確認・再設定は実運用Macで行います。`8445`が既存のServe設定と他の待受processで使われていないこと、転送先のHTTP入口が応答することを先に確認します。静的assetとAPIがルートからの絶対パスを使うため、他アプリとのパス分割ではなく専用ポートを使います。

```bash
tailscale serve status --json
lsof -nP -iTCP:8445 -sTCP:LISTEN
curl --fail --max-time 10 --output /dev/null http://127.0.0.1:8888/
tailscale serve --bg --https=8445 http://127.0.0.1:8888
tailscale serve status
```

`--bg`で設定したServeは終了操作まで保持され、Tailscaleの再起動後も再開します。利用にはMacの稼働・Tailscale接続・転送先Webの起動が必要です。WebのLaunchAgentは利用者のログイン時に起動するため、Mac再起動直後のログイン前の利用は前提にしません。ServeはWebの起動・再起動を担当しません。Webを停止した場合はHTTPSからも利用できなくなります。

HTTPS入口だけを解除する場合は次を実行します。他のServe入口を維持するため、対象ポートだけを解除し、Serve設定全体を消す`tailscale serve reset`は使いません。

```bash
tailscale serve --bg --https=8445 off
tailscale serve status
```

HTTPS追加は直接HTTPの閉鎖や自動転送を行いません。LANからの直接HTTPを閉じる場合は、LaunchAgentのbindをloopbackへ変更する別の運用切替が必要です。Serveの設定・永続化については[Tailscale公式CLIガイド](https://tailscale.com/docs/reference/tailscale-cli/serve)、tailnet内の公開範囲については[Serveガイド](https://tailscale.com/docs/features/tailscale-serve)を参照してください。

## 画面構成

| 画面 | 主な用途 | DB変更 |
| --- | --- | --- |
| `レビュー` | 要レビュー一覧、紹介確認、紹介候補一覧、一般の重複候補または任意の組み合わせを含むマージ候補の比較 | 操作を確認した時だけ書き込み。skipは書き込まない |
| `登録プロジェクト` | 登録プロジェクトの検索・詳細表示、シードのプレビュー・追加 | 検索は読み取り専用。明示した編集・操作だけ書き込み |
| `処理・定期実行` | `enrich`、外部情報の取り込み（`sync`）、追跡状態の見直し、定期実行設定 | dry-runとexecuteを画面で区別 |
| `設定` | 一覧件数、マージ方法、表示time zone、token、サーバー・DB情報 | UI設定はlocalStorage。サーバーのreloadはDBを変更しない |

検索条件、選択中の登録プロジェクト、詳細タブはURLに保存され、reload、back、forwardで復元します。tokenとUI設定はURLへ残しません。

## 登録プロジェクト

### サイトから記録

[Firefox拡張](../../extras/firefox-registry/README.md)のボタン、または登録プロジェクト一覧の`サイトURLから探す`から、見ているサービス・リポジトリの登録状況を確認できます。拡張はポップアップでWeb UIを試用でき、選んだプロジェクトや検索条件を`タブで開く`へ引き継げます。未保存の入力は引き継がないため、編集は移動先で行います。設定で従来の別タブ表示にも戻せます。元のサイトのタブは残ります。接続先の設定、小窓での認証、署名と継続導入、更新方法は拡張のREADMEを参照してください。

サービスの下位ページやGitHub等のリポジトリ配下を含めてURLを照合し、訪問先のドメインに対応する登録済みNSIDも検索します。たとえば`example.com`では`com.example.record`や`com.example.chat.message`を候補に含めます。`chat.example.com`では`com.example.chat.*`を探し、親や兄弟ドメインには広げません。採用済みURLへの一致があり、NSIDの一致も含めて1プロジェクトだけなら詳細を開きます。候補URLだけの一致、NSIDだけの一致、複数一致では、一致した値と採用状態を見て対象を選びます。同じドメインというだけでサービスやNSIDの帰属を採用しません。URLのクエリとフラグメントは照合へ渡しません。

一致が見つからない場合は名前・NSID等でも検索し、未登録なら`このURLで登録`から入力済みのシードをプレビューして登録します。この画面の手入力検索でも、ドメインやURLから同じNSID検索を行い、一致したNSIDを表示します。URL一致なしは未登録の証明ではありません。OAuth認可画面など元のサービスとURLが異なる場合も、サービス名やURLを検索して対象を選べます。URLの一致候補がある場合の登録ボタンは無効になり、先に候補を確認できます。NSIDだけの一致では登録ボタンを使えるため、既存候補との関係を確認してから追加します。閲覧・照合・検索だけではDBを変更しません。

詳細上部から次の操作へ進めます。

| 操作 | 記録する内容 |
| --- | --- |
| `紹介予定に入れる` | 紹介したい対象を理由・メモ付きで取り置く。`レビュー`→`紹介予定`で名前・理由を検索し、後から回収・理由編集・解除できる |
| `帰属を確認` | 識別子タブでサービス・リポジトリ・NSIDの候補を選び、理由を添えて採用する。未登録の値は`シードを追加`から登録する |
| `Lexicon利用を記録` | 保存済みのサービスURL、利用するcollectionのNSID、根拠URL、確認内容・理由を指定して保存する。NSIDの所有は採用しない。記録一覧から解除できる |
| `30日間保留` | 「エラーで使えなかった」等の理由を残し、期限または根拠変化まで紹介候補の再確認を待つ |

紹介予定は人が選んだ取り置きで、自動推薦の順位・保留・紹介済み状態とは独立です。推薦対象から外れたものや紹介済みの対象も、取り置きを解除するまでは紹介予定に残り、現在の状態を表示します。紹介後に取り置きを外す操作は明示的に行います。

Lexicon利用の記録では、OAuthの要求権限の宣言と、利用者が確認した利用関係を区別します。拡張はスコープを自動取得・解釈しません。判断を支える内容を理由へ記録してください。根拠URLもクエリとフラグメントを除いて保存します。保存後は`記録したLexicon利用`と`関係`、判断の履歴は`手動判断`から確認できます。

### 検索と詳細

採用状態は`識別子`、登録起点の採用判断は`手動判断`、採用来歴の詳細は`JSON`で確認します。対象未採用の追跡中projectは要レビュー一覧に出ます。候補の採用は`識別子`、project全体の処遇は既存の追跡状態の選択から判断します。最後の採用済み対象を除外・保留しても別候補を自動採用しません。

検索欄は名前・識別子・URLに加え、保存済みの短い紹介文（`tagline`）、説明（`summary`）、特徴（`features`）からも探せます。入力した文字列の部分一致で、複数語の意味検索や取得したページ・READMEの全文検索は行いません。

一覧の`シードを登録`と詳細の`シードを追加`はNSID、リポジトリURL、サービスURLをプレビューしてから登録します。自動判定を上書きする場合は`repo_url: https://forge.example/dev/app`のように入力します。既存の登録プロジェクトの詳細画面から追加した値は、その登録プロジェクトの所有NSID、サービス、ソースリポジトリとして採用され、採用判断と入力元を別々に保存します。同じ値を再適用して旧データの不足を補えます。

サービスURLのパスは保持します。`https://example.com/tool-a`と`https://example.com/tool-b`を別プロジェクトの入口として登録できます。利用者が明示したサービスURLは、パス名だけを理由に補助ページ扱いにしません。同じURLの除外・保留は最新の明示登録で解除し、親URLに対する再付着防止・保留の判断は残します。

フィルターで次を絞り込めます。

- 追跡状態、サービス状態、atprotoへの寄与度、notes・introduced・候補・エラーの有無
- 識別子の種類、値、採用状態（`classification`）
- 関係の種類、関係元（`subject`）と関係先（`object`）の種類と値、情報源
- 手動判断の種類、対象の種類・値、有効・期限切れ・解除済み

追跡状態、サービス状態、atprotoへの寄与度は複数選択です。識別子の種類・採用状態、関係の種類、関係元・関係先の種類、手動判断・対象の種類は選択肢から指定します。識別子・関係・手動判断の値は部分一致、関係の情報源は候補付き完全一致です。`メモ`の有無はプロフィールの利用者向け`notes`だけを対象とし、手動判断に付けた理由メモや`system_notes`は含みません。未選択のフィルターは絞り込みません。

登録プロジェクトの詳細画面は次のタブに分かれます。

| タブ | 表示内容 |
| --- | --- |
| `概要` | プロフィール、代表公式サイトと採用済みサービス一覧、用途別の`リンク・資料`、サービス・所有関係、保存済み結論の理由を示す`判定理由`、マージ候補、メモ |
| `識別子` | 採用状態と役割（`role`）付きの識別子、候補への操作 |
| `関係` | 種類付きの関係根拠、除外・保留操作 |
| `調査履歴` | 最新の調査実行記録、収集結果・失敗、履歴、保存済みの根拠、再評価 |
| `手動判断` | 有効な制御と手動判断の履歴 |
| `JSON` | schema v2 APIが返した登録プロジェクトのデータ |

`概要`の判定理由は保存済み状態を表示し、ネットワークやLLMを使いません。全登録プロジェクトとの比較が必要なマージ候補は詳細本体の後に別リクエストで計算し、DBへ保存しません。保存データがない項目は「未観測」（`not_observed`）であり、否定結果ではありません。

画面を移ると以前の詳細・マージ候補の通信を取り消します。別タブには影響しません。候補計算には全件比較の時間がかかり、通信取消し後もサーバー側の計算が停止するまで時間がかかる場合があります。

マージ候補は、同じ識別子がこのプロジェクトでは候補、別のプロジェクトでは採用済みの場合も拾います。一致した値・役割・双方の採用状態を見て、候補を採用する前に`マージ前に比較`へ進めます。採用済み側から候補側も探せます。開発者の共有、利用・参照しただけのcollection、旧構成要素・開発試験用、除外・有効な保留に当たる値は、この一致の対象にしません。別プロジェクト指定のある組も候補から外します。

サービス・所有関係の`OAuth scope の宣言`では、取得元と時刻、書込み対象と操作、RPCの宛先、未解決の権限セット、元のscopeを確認できます。これはアプリが要求できる権限で、実際に許可された権限やデータ利用の実績ではありません。認証用の`atproto`だけでも公開データを読めるため、「認証しか使わない」とは判定しません。以前の調査でrelationだけを保存した情報は従来の保存情報として表示し、新しい内訳は再調査後に得られます。

同じ欄の`コレクションごとの材料`で、同名のcollectionについて要求操作・Lexiconの説明とfield・record観測をまとめて確認できます。schemaのfieldが未保存の場合と、recordサンプルで観測したfieldを区別します。個別repo宣言やrecordサンプルがないことは非利用の証明ではなく、recordがあっても作成アプリは未確認です。

`atproto利用の関連記述`では、ページ本文・ページ説明・README抜粋にあるPDS等の語や、観測済みcollection名の周辺を確認できます。取得元、時刻、検索対象内の位置、省略の有無を表示します。検索候補には否定・予定・別サービスの説明も含まれ、主機能との関係は未判定です。取得後に初めて分かったcollectionは保存済み本文の範囲で検索するため、切捨て済みの説明やJavaScriptで初めて表示される本文を、この表示だけで補うことはできません。

`識別子`に表示するDIDとhandleは、`https://pds.ls/at://...`形式のアカウント参照へリンクします。

`リンク・資料`は、利用・インストール先、プロジェクト情報、補足情報、その他の順にまとめます。App Store、Google Play、F-Droid、配布ページは利用先として先に表示し、changelogやWeb Manifestは補足情報として分けます。未知のroleも削除せず`その他`に表示します。

詳細画面から次を実行できます。

- 単体`enrich`、追跡状態の変更、シードの追加・再適用
- 識別子候補の採用・除外、識別子の再付着防止・保留、関係の除外・保留
- 紹介候補の期限付き保留、候補の優先度を下げる手動判断、分割、別プロジェクト指定の解除、マージ候補の比較
- profileの`name`、`tagline`、`summary`、`features`、`introduced_url`、利用者向け`notes`のプレビュー・保存

変更は確認後にSQLiteへ保存します。profile編集はプレビュー後に登録プロジェクトが別プロセスで変わっていた場合、保存を拒否して再読込を促します。`system_notes`は機械生成履歴で、profile編集の対象ではありません。概要では件数だけを表示し、履歴は必要な時に展開できます。

説明を編集すると自動反映を解除します。`根拠のある説明変更を自動反映する`を明示的に選ぶと、以後の根拠付き変更を自動反映できます。来歴不明の既存説明は保護側です。更新案がある場合、編集で理由・根拠・提案文を確認し、`更新案を編集欄へ読み込む`→必要な修正→プレビュー→適用で採用します。`この更新案を見送る`では説明を変えず提案を取り下げます。同じ文面・根拠の案は再提示しません。preview後に入力を変えると再previewが必要です。

概要の`確認時点`は最新試行と最後に利用画面を確認できた日時を分け、取得失敗や観測差を補足として示します。用途・技術的特徴の説明はそのまま読み続けられます。時点が保存されていない観測は未記録と表示します。これらは認証後の機能や現在の稼働保証ではありません。

`概要`の`サービス・帰属`では、保存済みの採用済み・候補（`confirmed` / `candidate`）サービスURLを選び、匿名ブラウザー確認をバックグラウンドジョブとして開始できます。任意URL、認証情報、フォーム入力は受け付けません。実行結果は確認後にSQLiteへ保存され、サービス状態と根拠へ反映されます。実行にはPlaywrightとブラウザーの導入が必要です。

識別子の再付着防止・保留・分割は、同じ値のrole単位ではなく、画面に示す識別子全体へ作用します。保留解除は自動採用ではありません。

登録プロジェクトの「絞り込み」→「Lexicon」ではspace、record、非record、宣言先の公開活動が未観測のものを選べます。詳細の「Lexicon公開情報」は型・発行元・宣言先と一覧取得時点を表示します。spaceの宣言は所有や実利用の確認とは別です。取得失敗・未取得は活動を比較できない状態として表示します。

## レビュー

`editorial_refresh`は保護された説明への更新案、`service_observation_changed`は利用面または保存範囲のページ内容の変化です。後者だけで機能変更や終了が確定したわけではありません。`out_of_scope`についてはこの2種の新しい材料も通常一覧へ表示し、説明と追跡状態をそれぞれ見直せます。

`要レビュー一覧`は要レビュー項目、`紹介候補一覧`は紹介候補、`マージ`は一般の重複候補または直接入力した任意の組み合わせを表示します。`要レビュー一覧`の`要レビューの種類`で日本語の項目を選ぶと、その種類だけに絞り込めます。適用中の条件はURLへ保持されるため、再読込やURLの共有後も復元されます。`紹介候補一覧`の候補カードでは、利用画面の確認状況、追加確認が必要な理由、並び順に使うスコアを確認できます。スコアの内訳は詳細の`評価`にある`紹介スコアの内訳`で開きます。保留の理由・期限、優先度のメモ、手動判断の根拠もカードで確認できます。

`紹介候補一覧`の「候補の扱い」は、普段見る「確認対象」、技術面から選ぶ「技術候補」と、あとで拾う「保留」「低優先度・特集候補」「すべて」に分かれます。理由を部分一致で検索でき、「理由別の候補数」から同じ理由の対象をまとめて探せます。各一覧の「次のページ」で件数上限より先も確認できます。条件とページ位置はURLに保存します。

「確認対象」と「技術候補」は追跡状態`active / stable`を通常対象とし、`stalled`は含めません。紹介済み、保留中、優先度を下げた対象は、`stable`であっても通常候補には戻りません。

「技術候補」はサービスの利用可能性と独立して技術的な学びのある候補を並べ、カードにその理由を表示します。`high / exceptional`の未確認候補が対象で、優先度を下げた候補や保留にした候補はそれぞれの専用一覧から探せます。

カードと詳細の「主機能でのatproto利用」には手動判断と根拠を表示します。詳細の「利用範囲の判断を記録」から理由付きで保存し、必要なら解除して未評価へ戻せます。例えばプロフィールだけをatprotoに置くサービスは「補助的な利用」、既存投稿の管理ツールは「Bluesky専用操作」と記録できます。OAuth宣言と関連記述を参考に判断し、LLMやサービス確認度だけでは利用範囲を自動確定しません。

詳細上部の「紹介候補の判断」で次の操作を選べます。

| 操作 | 意味と再発見方法 |
| --- | --- |
| `30日間保留` | 理由は任意。30日間は通常候補から外し、期限または根拠変化で戻す。「保留」で理由・期限の確認と解除が可能 |
| `優先度を下げる` | 単体で先に取り上げない候補、同じ理由をまとめて特集したい候補を保存。「低優先度・特集候補」で検索・理由編集・通常優先度への復帰が可能 |
| `今回は先送り` | 今の表示だけ先送り。保存せず、再読込で再表示 |

例えば「認証のみ・まとめて特集」という理由を付けておけば、後日「認証」で検索できます。優先度を下げる操作は不要・低品質を意味しません。理由は任意ですが、検索に使う共通の語を入れると拾いやすくなります。根拠変化によって明示した優先度を自動で元へ戻すことはありません。

再確認を促す変化は、サービス状態、確認済み識別子、技術評価、機能情報等です。単なる再取得時刻や説明の言い換えだけでは戻しません。理由文の「この機能が実装されたら」等を理解して条件達成を保証するものではないため、再表示された内容を確認してください。判断時の根拠情報を持たない古い保留だけは、期限で復帰する元の条件を維持します。以前の「確認済み」は期限と記録を引き継いで「保留」にまとめます。

専用一覧には、現在の推薦理由がなくなった候補や調査範囲外の保存候補も残します。表示された追跡状態を確認して扱ってください。「すべて」は候補と保存済みの判断対象の集合で、全登録プロジェクトの検索は`登録プロジェクト`です。

判断を保存すると、表示中のカードだけを外して次へ進みます。表示中の候補を確認し終えたら`再読込`で先頭から最新候補を取り直します。一覧や詳細を開いたこと、再読込したこと自体は判断として記録しません。

マージ候補の比較では、マージ元からマージ先へまとめる向きで、両方の登録プロジェクトのprofile、状態、シード、識別子、候補となった理由、マージ結果のプレビューを比較します。マージ先のプロジェクトIDと同優先度の値が残るため、`マージ元とマージ先を入れ替える`で向きを入れ替えてプレビューできます。`別プロジェクトとして保持`は2件を別の登録プロジェクトとして扱う手動判断を保存します。`プロジェクトをマージ`は確認後にマージします。統合後の登録プロジェクトに別のマージ候補が残る場合は、一覧全体を再計算せず、その次候補の比較へ進みます。候補一覧にない組み合わせもプロジェクトキーを直接指定して比較できます。

設定のマージ条件が`標準`（moderate）または`広範`（broad）なら、候補と採用済みの同一識別子だけで一致した組も一覧へ含みます。一覧では互いに最上位候補であることが必要なため、個別ページで見つかる候補がすべて載るわけではありません。識別子を共有する別プロジェクトの場合もあるため、この一致だけでは自動マージ可能にしません。値や採用状態の表示を確認し、比較画面で1組ずつ判断してください。

比較画面の「Lexicon発行元とrecord初回観測者」では、保存済みのLexicon発行元DIDと発行元同士の一致を追加通信なしで表示します。「record初回観測者を照会（外部通信）」を押すと、外部APIが先頭に返す利用者のDIDを取得し、発行元との交差比較と初回観測者同士の一致も表示します。型が判明した非recordは照会せず、型不明のNSIDは照会対象です。主要な結果は直接表示し、双方の照会結果と発行元の出典・観測日時・検証状態は個別に展開できます。未検証や期限切れなどの公開観測は検証済み発行元の一致に使いません。一致は所有者や絶対的な最初の作成者、同じプロジェクトであることを確定せず、候補スコアや自動マージ条件にも使いません。

複数利用者が使うホスティングサービスの接尾辞がPublic Suffix List（PSL）にないためにマージ候補になったと考えられる組み合わせでは、接尾辞候補を表示し、その場で`domain-overrides.json`へ追加できます。接尾辞の追加は今後のドメイン判定を変えるため、プレビュー内容を確認してください。

## 処理・定期実行

バックグラウンドジョブはWebサーバーとは別プロセスで動き、同じWebサーバーでは同時に1件だけ実行できます。CLIなど別プロセスとの排他は行いません。

総件数が分かるジョブは進捗を`現在 / 総件数`で表示します。総件数が事前に分からない紹介済み投稿（introduced情報）の取り込みは、取得済みページ数を表示します。

### 調査

単体または一括実行を選び、詳細調査、未`enrich`のみ、前回失敗分のみ、追加の追跡状態を指定できます。一括`enrich`は登録プロジェクト間で停止し、チェックポイントから再開できます。同じ登録プロジェクトへの編集等と競合した場合、現在状態を守り、調査成果を調査履歴へ「未反映（競合）」として残します。他の対象は続行し、競合だけが残ったjobは再試行待ち（`retry_wait`）になります。再開は最新状態から再調査するため、外部取得・LLMの処理時間が再びかかります。一般障害は`failed`として区別します。

### 外部情報の取り込み

設定済みのintroduced、GitHub、collection一覧、Semble、Tangledから外部情報を取り込みます。任意の検索条件やURLはCLIで指定します。dry-runでは取り込み候補を確認でき、外部ネットワークへ接続しますがSQLiteは更新しません。停止要求は現在の情報源のページ・項目境界で反映され、チェックポイントからの再開はありません。

introducedの保存実行で取得した投稿は、URLが自動照合できなかった理由とともに`レビュー`→`紹介確認`へ残ります。投稿本文は対象URLを含む行だけを表示し、確実に特定できない場合は省略します。`元の投稿を開く`から全文を確認できます。名前付きの一致候補から紐付け先を選び、候補にない場合は登録プロジェクトを検索します。選択すると`詳細を確認`でプロジェクト詳細を別タブに開けます。元の紹介確認の項目・候補選択・検索語・検索結果は残り、同じページ内で項目を切り替えて戻った場合も選択・検索状態を保ちます。ページの再読込では候補選択・検索状態は解除されます。`このプロジェクトに紐付ける`と確認ダイアログで紹介投稿URLを設定し、選択や詳細閲覧だけでは保存しません。詳細閲覧は必須ではありません。URLまたは投稿を対象外として記録することもできます。

紹介URLの設定は識別子の候補を採用しません。登録プロジェクトに別の紹介URLがある場合は、元と新しいURLを示して付け替えを確認します。複数一致で同期が先頭の登録プロジェクトへ紹介URLを設定した場合、別の登録プロジェクトへの紐付けや対象外判断でその自動設定を外します。同じ投稿の別URLも先頭へ一致する場合は維持します。`判断済みを含むすべて`から手動判断を取り消し、要確認に戻せます。抽出済み識別子は`再照合`で現在の登録状態と照合できます。

一覧の上部に直近の取得が未完走だったか、watermarkと取得投稿数を表示します。要確認0件は検索結果の完全取得を意味しません。従来の未一致保留は投稿本文を持たない状態で同じ一覧に表示されます。

TangledはJetstream v2 snapshotを使います。Webサーバー環境に`ATPROTO_SURVEY_JETSTREAM_API_KEY`とNode.js 22.15以上、ワークスペースに`npm install`済みの公式SDKが必要です。APIキーはUI、ジョブ設定、結果へ保存しません。通常は1回1,000イベントを上限として、途中終了時の処理位置（sequence）から次回の取り込みを再開します。

Lexiconの公開からも候補を取り込めます。通常の定期取り込みではcollection一覧の次に実行し、最後に未調査projectだけを調査します。schemaが追加・変更された調査済みprojectの説明は、通常の週次調査または個別の「調査」で更新します。

### 追跡状態の見直し

保存済みの登録プロジェクト情報から、`stalled`・`stable`、調査範囲外、追跡対象外への変更候補を再計算します。適用内容の作成はネットワークを使いません。dry-runで候補を確認し、execute時は表示対象を一括適用します。

### 定期実行

`サービス観測`は未確認・古いconfirmed service URLを最大20件、匿名browserで確認します。前回試行から30日以上を対象にし、`active / stable / stalled / out_of_scope`を含めます。初期設定は無効、毎週土曜03:00です。ジョブ結果の対象数・残件・失敗・観測差を確認し、実データ量に応じて運用を決めてから有効化します。上限があるため全対象を毎月確認できるとは限りません。説明生成・追跡状態変更はこのpresetでは行いません。

許可済みの定期実行設定だけを手動または定期的に開始できます。任意のコマンドは実行できません。設定できるのは通常の一括`enrich`、全追跡状態の見直し、introduced情報の取り込み、その他の外部情報を取り込んだ後に行う新規登録分だけの`enrich`です。全追跡状態の見直しに続くstalled reviewは、候補件数で打ち切らず全候補を反映します。

各設定は有効・無効、毎週または月の第N週、曜日、時刻、time zoneを持ちます。設定と実行待ち一覧はDBと同じディレクトリの`job-schedules.json`へ保存します。予定から24時間を超えた未実行分は後から実行しません。サーバー再起動時に実行中だった段階は完了扱いにせず、同じ段階から再試行します。

競合後も独立したsourceの取り込みと保存済み新規projectの調査は続行します。全状態enrich後のstalled reviewは調査完了まで保留します。一般障害・明示中断・処理用workerの起動失敗では、その定期実行設定の後続処理を停止し、失敗・中断した段階と未完了の後続処理を保留します。

保留する処理と理由は定期実行に表示し、`保留中の処理を再開`で再開します。成功済みの取り込みやレビューは繰り返しません。一括`enrich`は利用可能なチェックポイントから再開し、チェックポイント作成前の障害では同じ条件で新しく実行します。取り込みと追跡状態レビューは、失敗した段階を最新状態から再実行します。再試行した取り込みで増えた未調査projectも、その後に調査します。保留はサーバー再起動後も残り、同じ定期実行設定は次の週・月の予定時刻でも自動再試行しません。保留がなくなった後の`今すぐ実行`は、設定された処理全体を新しく開始します。

### ジョブ履歴と再起動

ジョブ一覧とイベントはサーバープロセス内だけに保持され、サーバー再起動後は復元されません。一括`enrich`の未完了チェックポイントは`保存済みの再開地点`から再発見・再開できます。外部情報の取り込みと追跡状態の見直しにはチェックポイントからの再開がありません。

設定の`サーバーを再起動`はWebプロセスを再起動し、SQLiteは変更しません。実行中のジョブへ協調停止を要求し、タイムアウトを超えたworkerは終了してから再起動します。ブラウザーは新プロセスの応答後に自動再読込します。LaunchAgentからの停止時も同じworker終了処理を行います。

## 設定

- 一覧・登録プロジェクト・マージ候補の件数上限、マージ方法、personal toolの包含
- 表示time zone。既定`Asia/Tokyo`、IANA名または`+09:00`形式
- 保存済みAPI tokenの削除（再入力は削除後のページ再読込時）
- 接続DB、Python version、起動時Git commit/dirty状態
- サーバーのreload（画面からの終了機能はない）

表示time zoneを変えてもDB timestampは変わりません。Git状態はサーバー起動時に一度取得するため、checkout変更後はreloadが必要です。

## アクセス境界

Web UIは1人の利用者が使う前提です。手動起動の既定は`127.0.0.1`ですが、実運用のLaunchAgentは管理下のLANから使うため`0.0.0.0:8888`へbindします。公開サーバー、共有端末、複数利用者向けのアクセス制御はありません。

- 起動時の初回URLだけqueryにtokenを含み、UIは読取直後にURLから除去します。ただしターミナル、ブラウザー拡張、初回navigationを観測できる相手からtokenを守る仕組みではありません。
- tokenは同じoriginの`localStorage`へ保存されます。同じブラウザープロファイル・originを使えるスクリプトや利用者とは秘密を分離できません。不要になったら設定の`APIトークンを削除`で削除してください。
- アプリ本体はplain HTTPで、token rotationを提供しません。実運用では前段のTailscale ServeからHTTPSでも利用できます。直接HTTPは残っているため、LaunchAgentを使うLANと端末は管理下に限定し、internetへport 8888を転送しないでください。
- LAN外から使う場合は[Tailscale経由のHTTPS](#tailscale経由のhttps)を使います。直接HTTPを閉じてHTTPS経由だけに限定する運用切替は未実施です。

APIリクエストは共有token必須です。起動時URLのbootstrap token、`Authorization: Bearer ...`、`X-Project-Registry-Token`のいずれかを使います。静的assetはtokenなしで配信します。
