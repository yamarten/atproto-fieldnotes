# Project Registry 利用ガイド

候補を登録し、調査結果の根拠を読み、次に深掘りする対象を選ぶまでを案内します。画面を先に見たい場合は[READMEの試用デモ](../../README.md#架空データで試用デモを動かす)から始めてください。デモを試し終えたらWebをCtrl+Cで止め、このガイドの「自分の調査DBを用意する」へ進めます。

## 環境準備

リポジトリを取得し、そのルートディレクトリで以下を実行します。[uv](https://docs.astral.sh/uv/getting-started/installation/)とNode.js 22.15以上が必要です。macOSでHomebrewを使っている場合、uvは`brew install uv`で導入できます。

```bash
bin/project-registry-python-env prepare initial
bin/project-registry-python-env activate initial
npm install
```

Python本体と依存はcheckout内へ取得します。既定はCPython 3.14の最新patchで、起動のたびに更新することはありません。Node依存はTangledの取得とOAuth scopeの解析に使います。既に環境がある場合は準備を繰り返さず、`bin/project-registry-python-env status`で確認してください。更新・復旧は[Python環境の管理](python-environment.md)を参照します。

以下では`bin/`をPATHに追加してコマンドを使います。追加しない場合は`project-registry`を`bin/project-registry`のように読み替えてください。

## 自分の調査DBを用意する

```bash
export PATH="$PWD/bin:$PATH"
project-registry init-db
```

新しいDBを`data/survey.db`へ作ります。既存DBは上書きしません。READMEのサンプルDBとは別なので、試用時の判断や架空データは入りません。通常のCLIとWebはこのDBを使い、存在しないDBを暗黙には作成しません。

次に[接続設定](configuration.md)で、調査に使うLLMと必要な外部情報源を設定します。LLMは説明・分類やリポジトリ解析に使います。未設定でも保存済みデータの閲覧・手動編集はできますが、LLMによる調査結果は得られません。GitHub・Bluesky・Tangledの認証は利用する取得経路に合わせて設定します。

設定した環境からWebを起動します。`ATPROTO_SURVEY_WEB_TOKEN`はWeb UIへログインするための合言葉です。以下の値を自分用に置き換え、ブラウザーの初回入力にも同じ値を使います。

```bash
export ATPROTO_SURVEY_WEB_TOKEN='your-web-login-token'
project-registry-web --host 127.0.0.1 --port 8765
```

表示されたURLを同じ端末のブラウザーで開きます。tokenをURLに付けずに開く場合は、最初の入力ダイアログへ同じ値を入力します。終了は起動したターミナルでCtrl+Cです。macOSで継続利用する場合の[自動起動](web-ui.md#macosでの自動起動)は、一通り試してから設定できます。

## 日常フロー

### 1件を登録して調査する

たとえば、気になるサービスのURLやリポジトリ、LexiconのNSIDを見つけたら、それを「シード」として登録します。シードは調査の起点です。入力した値をその対象のサービス・ソースリポジトリ・所有NSIDとして採用するので、単に言及されていたURLや借用しているcollectionとは区別してください。

1. `登録プロジェクト`の`シードを登録`を開き、値を入力してプレビューします。既存の登録先があるか、何の種類として解釈されたかを確認して登録します。
2. 登録したプロジェクトの詳細から`調査`を押します。外部情報源へ接続し、収集・解析した結果と調査履歴をDBへ保存します。
3. 結果の`概要`を開きます。用途、サービスの利用可否、atprotoとの関係を読み、何が分かり、何が未確認かを確かめます。

CLIなら同じ流れは次の通りです。例はTangledのNSIDで、調査時には実際の外部取得と設定済みLLMを使います。

```bash
project-registry add-seed sh.tangled.repo
project-registry enrich --seed sh.tangled.repo --type nsid
project-registry show --seed sh.tangled.repo --type nsid
```

登録対象は`proj:xxxxxxxxxxxx`形式のキーで管理されます。既存対象へシードを追加する時は詳細の`シードを追加`、CLIでは`add-seed ... --project-key KEY`を使います。対応する入力形式は[扱うシード](#扱うシード)、正確な引数と出力は[CLIガイド](cli.md#登録調査表示)で確認できます。

### 紹介へつなげる

紹介する対象の名前・短い説明・URLを作るために、まずtagline・summaryで内容をつかみ、公式サイトやリポジトリから個別に確認します。説明生成は下書き作成も目指していますが、現状では説明の弱さと対象自体の価値を同一視できません。NSIDやアカウント、特徴、評価は必要な時に補助として参照できます。調査材料の読み方は[atprotoの活用事例を調べる](research-methods.md)を参照してください。

名前・説明は調査で自動生成され、入力不足やLLMの誤りで不適切になることがあります。例えば「栞棚」が「example shioridana bookmark」と名付けられた場合は、公式の呼称を確認してプロフィール編集で訂正します。手動編集後の更新案と自動反映の扱いは[紹介候補を選び、判断を残す](#紹介候補を選び判断を残す)で説明します。

### 結論から根拠へたどる

`概要`は調査結果の入口です。自動生成された説明や「利用可能」の表示を読むだけで判断しきれない時は、次の場所を確認します。

| 確かめたいこと | 開く場所 |
| --- | --- |
| いつ、どこまで確認できたか | `概要`の`確認時点`。最新の試行と最後に利用面を確認した時点を区別する |
| URLやNSIDが本当にこの対象に属するか | `識別子`と`関係`。候補と採用済み、根拠の種類を確認する |
| 取得失敗や説明の裏付け | `調査履歴`。保存済みの収集結果と根拠を読む |
| 自分が以前どう判断したか | `手動判断`。採用・除外・保留などを確認する |

一部の取得に失敗しても、得られた材料と失敗は区別して保存されます。未観測は否定結果ではなく、古い成功も現在の稼働保証ではありません。説明は用途・機能・技術的特徴を残すためのもので、一時的なアクセス失敗だけで書き換えません。

### 評価を使い分ける

次の表示はそれぞれ異なる問いに答えます。たとえばLexiconを取得できて「atproto寄与度」が高くても、そのサービスの主機能がatprotoで動くとは限りません。

| 表示 | 何の判断に使うか | 読み取りの限界 |
| --- | --- | --- |
| サービス状態・確認時点 | 利用を試せそうか、改めて確認すべきか | 保存済みの観測・評価。認証後の機能や現在の稼働を保証しない |
| atproto寄与度 | NSID・schema・record等、調査で得たprotocol上の材料の強さを見る | 規則による評価。名称の「中核的な利用」も主機能での利用範囲を確定するものではない |
| 主機能でのatproto利用 | 主機能、補助部分、Bluesky操作、認証のどこに使うかを判断して残す | 理由付きの手動判断。未評価と非利用を区別し、OAuthの要求権限だけでは確定しない |
| 技術的な学び | protocol設計・相互運用・実装上、深掘りしたい点を探す | LLMによる暫定評価。理由と根拠を読み、サービスの利用可否とは別に判断する |
| 紹介スコア | 紹介候補をどの順で確認するかの参考にする | 紹介価値の絶対点ではない。利用面・技術評価・情報充足等の内訳に加え、保留や手動優先度も一覧の扱いを左右する |

紹介情報に不足がある対象も、サービス・Lexicon公開・技術面の理由から紹介候補に載ることがあります。不足情報の表示は「次に何を補うか」、候補への掲載は「どれを確認するか」の材料です。atproto寄与度の点数は要レビュー一覧の順位に使いますが、紹介候補の順位で主機能の利用範囲の代わりには使いません。細かな条件は[評価仕様](../developer/specs/project-evaluation.md#稼働状態とatproto寄与度)を参照してください。

### 紹介候補を選び、判断を残す

外部情報からの新規登録でも、最初の調査対象を採用してから調べます。採用状態は`識別子`、登録起点の採用判断は`手動判断`で確認できます。採用済みは発行元の真正性を保証する表示ではありません。対象が騙りならプロジェクト自体の追跡状態を見直せます。最後の対象を除外・保留しても別の候補は自動採用せず、対象未採用としてレビューを促します。

`レビュー`には、曖昧な帰属などを処理する`要レビュー一覧`と、深掘りする対象を探す`紹介候補一覧`があります。紹介候補は、atprotoで何をどう実現しているかを知り、紹介する題材を選ぶ入口です。原文や実サービスを確認して紹介可否を決めます。候補一覧の選定を補う場合はプロジェクト一覧の新規登録順も使えます。登場直後で発展を期待できる対象にも注目しますが、新規登録日時はサービスの公開日時とは異なります。

見慣れた候補を毎回確認すると、新しく深掘りしたい対象が埋もれます。今は調べない対象は`30日間保留`、単独で紹介するには弱くても、同じ類型をまとめてなら紹介できそうな対象は`優先度を下げる`で判断を残せます。低優先度は通常の確認対象から外れ、「低優先度・特集候補」で理由から探せます。戻すまで有効で、品質の否定や追跡停止を意味しません。`今回は先送り`は判断をまだ決めず、DBへ保存せずにその一覧で次へ進む操作です。[保留の再表示条件と一覧操作](web-ui.md#レビュー)を参照してください。

説明を直す時は`概要`の`紹介情報`から`編集`を開き、プレビュー後に保存します。人が編集した説明は自動上書きから保護され、後の調査で更新案が出た場合に根拠と差分を確認できます。紹介文の公開はこのツールの外で行い、公開後の投稿URLを紹介済み情報へ記録します。[レビューの操作](web-ui.md#レビュー)と[説明編集](web-ui.md#登録プロジェクト)に詳細があります。

### 候補を増やし、継続して追う

1件の流れをつかんだら、`処理・定期実行`から外部情報の取り込みや一括調査を使えます。取り込み（`sync`）はまず候補を確認し、保存する実行を選びます。情報源ごとの対象・上限は[収集設定](configuration.md#設定ファイルと認証情報)で調整します。

通常の調査を続ける対象、安定稼働している対象、追跡しない対象は[追跡状態](cli.md#共通の入力と出力)で分けます。通常の一括調査は`active`だけが対象で、状態を変えても情報は削除しません。状態だけで個別の調査間隔が予約されるわけではなく、追加対象と定期設定を選んで調査頻度を変えます。一括処理の進捗や停止・再開は[処理・定期実行](web-ui.md#処理定期実行)、低頻度のサービス確認は[CLIのmonitor-services](cli.md#調査開発補助)を参照してください。定期実行は対象と処理量を確認してから有効にします。

## 操作前に区別すること

Project Registryの操作は、次の3点を分けて判断します。

| 種類 | 意味 |
| --- | --- |
| 読み取り専用 | DBを書き換えず、外部情報源にも接続しない。`show`、`explain`、`audit-url-fields`、`audit-trust-graph`など。 |
| dry-run | DBへは書かないが、外部情報の取り込み（`sync`）やサービス確認は外部ネットワークへ接続することがある。 |
| 書き込み | 常時書くコマンドと、`--execute`または確認後だけ書くコマンドがある。 |

`enrich`は調査結果と調査実行記録を常にDBへ保存します。`add-seed`、`set-*`、`block-*`、`defer-*`も常時書き込みです。外部情報の取り込み、マージ、分割、修復、整理、履歴削除は既定がdry-runで、`--execute`を付けた時だけDBを変更します。

正本DBへ書く前は、Web UI、別のCLI、バックグラウンド処理が同時に動いていないか確認してください。特に修復、マージ、整理、履歴削除、`VACUUM`はバックアップを取り、DBへ書き込む処理を止めた保守時間帯に実行します。

別DBを使うCLIは`project-registry --db-path PATH COMMAND ...`、Webは`project-registry-web --db-path PATH`です。schema version 5のDBが必要で、`--db-path`は認証や外部アクセスを隔離する設定ではありません。初期化・移行やcheckpointの扱いは[CLIの共通事項](cli.md#共通の入力と出力)を参照してください。

## 扱うシード

シードの種類は`nsid`、`repo_url`、`service_url`です。通常は値から自動判定し、曖昧なURLだけ`--type`またはWeb UIの`type: value`形式で明示します。

`nsid`として、NSIDそのものに加えて次のURLも受け付けます。

- `at://did.../collection[/rkey]`
- `https://pdsls.dev/at://did.../collection[/rkey]`
- `https://pds.ls/at://did.../collection[/rkey]`
- `https://lexicon.garden/lexicon/did.../collection.nsid`

既知のforgeのfile/tree URLはリポジトリのルートURLへ正規化します。未知のforgeや曖昧なURLは`repo_url`を明示してください。

## 基本用語

| 用語 | この文書での意味 |
| --- | --- |
| 登録プロジェクト | Project Registryが1つの調査対象としてDBに保存する単位。コマンドやJSONでは`project`と表記される。 |
| シード | 登録プロジェクトを作成・特定する入力。NSID、リポジトリURL、サービスURLを指定できる。入力した値の役割、情報源、採用判断はそれぞれ保存する。 |
| 公式サイト（Website） | 人が登録プロジェクトを知るための代表的な公式URL。紹介、documentation、native appの配布pageでもよく、公式サイトであることだけでは識別子や信頼の起点にならない。 |
| サービスURL | 登録プロジェクトの機能を実際に提供するURL。Web app、API、PDSなどが該当し、1つの登録プロジェクトに複数あってよい。公式サイトと同じURLでも別の責務として扱う。 |
| `enrich` | 登録プロジェクトを調査し、現在の情報と調査履歴を更新する処理。 |
| 外部情報の取り込み（`sync`） | 設定済みの外部情報源を走査し、既存の登録プロジェクトとの照合結果や新規登録候補を作る処理。 |
| 調査実行記録 | 1つの登録プロジェクトに対する`enrich`などの保存済み調査履歴。JSONでは`investigation run`または`run`と表記される。 |
| 追跡状態 | 継続調査上の扱いを示す状態。コマンドやJSONでは`tracking_state`と表記される。 |
| 要レビュー一覧 | 人による確認が必要な項目の一覧。CLIでは`review-queue`。 |
| 主機能でのatproto利用 | 主機能のデータ・基盤、補助的な利用、Bluesky専用操作、認証のみ、利用範囲は不明という理由付きの手動判断。サービスを利用できるか、技術的な学びがあるかとは別に記録し、LLMでは自動確定しない。 |
| 技術候補 | 具体的なprotocol設計・相互運用・実装上の学びを理由に選ぶ紹介候補。サービスの有無と独立した入口でも確認できる。 |
| 紹介候補の保留 | 確認対象から一時的に外す判断。理由は任意、既定30日。期限・根拠変化・明示解除で再評価できる。 |
| 紹介候補一覧 | 紹介する候補を選び、優先度や保留を判断する一覧。CLIでは`promotion-queue`。 |
| 分類 | 主な利用者と利用形態による登録プロジェクトの分類。保存値は`project`、`lexicon`、`library`、`infra_tool`、`personal_tool`、`name_only`、`reject`。詳しい境界は[Project Record Schema](../developer/specs/project-record.md#category)を参照。 |
| 採用 | 候補の識別子を、その登録プロジェクトに属するものとして利用者が認める操作。保存値は`confirmed`。この値は自動判定による採用にも使われ、利用者の操作は手動判断の記録で確認できる。 |
| 手動判断 | 採用、除外、保留、別プロジェクト指定など、自動判定より優先される利用者の判断。 |
| マージ | 重複した2つの登録プロジェクトを1つにまとめる操作。 |
