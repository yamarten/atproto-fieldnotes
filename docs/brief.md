# Project Registry Brief

## 目的

atproto関連のプロジェクト、サービス、ライブラリ、lexiconを継続的に発見・調査します。[ATプロトーク](https://www.bluecast.app/user/@yamarten.bsky.social)で紹介するプロジェクトの予備調査を主目的としながら、ATmosphereに関する情報を再利用できるローカルDBへ蓄積します。

このツールは、利用者が日常的に新しいプロジェクトを探し、同じような予備調査や短い紹介文の作成を繰り返す負担を減らすために始めました。発見と初期調査を機械化し、一度得た情報と判断を次の調査へ再利用します。

登録プロジェクトの同一性、活動状況、関連情報、紹介状況、情報の根拠、利用者の判断を一つの登録プロジェクト単位で追える状態を目指します。

## 利用者と成果物

利用者は、ローカルDBを運用する一人です。複数利用者での運用、共有DB、外部利用者向けAPIは対象にしません。

紹介内容の主な読者はatproto開発者です。サービス・共有Lexicon・基盤をatprotoの活用事例として集め、各ドメインの概念や操作をどこまでLexiconで表現できるか、どのような設計パターンが生まれているかを知り、紹介します。サービスの利用可能性は取り上げる際の足切り条件であり、利用できることだけを紹介価値とはしません。

紹介の完成形は「名前・短い説明・URL」です。ツールは、それを人が作るために、紹介候補と、公式サイト・公式リポジトリを中心とするリンク、名前・tagline・summaryを渡します。NSIDなどは補助出力であると同時に発見・調査にも使い、Sembleなどの収集元は発見や追加調査の入口として扱います。各情報の役割は[識別子と調査・出力の関係](developer/specs/project-boundaries.md#識別子を発見調査出力に使う目的)で区別します。

説明生成は、紹介文の下書きに使える品質を目指します。2026-10時点の利用では紹介文への直接反映は少なく、具体的な説明が書けている対象を個別に見に行く判断材料として使われています。この現状を最終目標に置き換えず、説明しにくい対象の取りこぼし、事実の誤り、補完・訂正の負担から改善を判断します。紹介文の公開はツールの外で行い、紹介結果を以後の調査へ戻します。

候補選定では、現在の内容の価値に加え、登場したばかりのサービスの速報性や発展への期待を扱います。2026-10時点では、ツール内の入口は紹介候補とプロジェクト一覧の新規登録順がほぼ半々で、外部発見も全体の1〜2割程度あります。新規登録順は選定の弱さと速報性を補う入口です。この人の補完負担を減らすことを目指しますが、台帳への登録日時をサービス自体の登場日時と同一視しません。

紹介対象の価値基準は暫定的に、第一に新しいLexiconを伴うサービスや共有Lexicon、次に特異な機能を持つインフラ実装を重視し、分散性に関わるAppView代替インスタンスも視野に入れます。Lexiconの存在と技術的な面白さは別で、面白い使い方があればさらに評価します。すべてに技術的新規性を必須とせず、実用性よりも自前buildなしですぐ触れる等の触りやすさを重視します。特定ブログ用などの個人用途は別に扱いますが、自動的な収集対象外を意味しません。

紹介対象になりそうな度合いは連続的に捉え、候補間の相対的な優先差を扱います。低優先を直ちにノイズとせず、情報不足とも区別します。この価値基準は運用に照らして見直せるもので、固定の配点・除外条件や現在の推薦実装の説明ではありません。

努力目標として、蓄積した情報から公開可能なプロジェクト一覧を生成できる状態を目指します。収集範囲は利用者が通常の人力調査で拾う情報を目安とし、機械化によって可能な限り取りこぼしを減らすことを重視します。公開手段の第一候補は、共有Lexiconとして標準に取り上げやすいLexicon Communityのapp record形式での書き出しですが、公開仕様の都合だけでDBの内部表現を決めません。紹介活動を続けなくなった場合にも、それまでに蓄積した情報を別の形で利用できる状態を残します。

## 開発の優先順位

1. 深掘りする価値がある候補を、背景と根拠とともに提示できる
2. 追加調査と紹介文の下書きに使える説明・リンクを保ち、訂正を引き継いで更新できる
3. 運用上必要なレビュー、登録プロジェクトのマージ、判断根拠を保てる
4. 公開手段の第一候補であるapp record exportへ、紹介用の情報を再利用できる状態を保つ

紹介フローを主導に置き、その延長でapp record exportの可能性を確保します。

具体的な残件と着手条件は[開発TODO](developer/todo.md)で管理します。

## 通常の運用フロー

1. 外部情報の取り込みと手動発見から候補を集める。
2. 既存の登録プロジェクトとの同一性や関係を保守的に判定し、曖昧なものを要レビュー一覧へ回す。
3. 深掘りする価値の判断に必要な情報と根拠を収集・更新する。
4. 利用者が深掘りする候補、曖昧な関係、追跡を続けるかどうかを判断する。
5. 判断結果をDBへ反映し、収集範囲、失敗、負担、保存量を継続的に見直す。

## 対象の境界

登録プロジェクトは、そのプロジェクトが所有するLexicon、主要実装、公式リポジトリ、提供サービス、代表サイト、ネイティブアプリなどを、一つの説明・追跡対象としてまとめる編集上の単位です。構成要素の完全な一覧は求めず、同じ開発者、リポジトリ、ドメインのいずれか一つを共有するだけでは同じ登録プロジェクトとみなしません。

紹介候補になり得るもの:

- 独立したatprotoプロジェクトやサービス。
- 独自lexicon、実用サービス、またはatproto ecosystemへの明確な技術的貢献を持つもの。

調査対象:

- 紹介候補か未確定だが、atprotoとの関連を示す根拠があるもの。
- ライブラリ、基盤、認証連携、personal toolなど、別の分類で保持する価値があるもの。
- 同一性や所有関係が曖昧で、利用者による確認が必要なもの。

記録のみ:

- 現在は紹介しないが、将来の再評価や既存の登録プロジェクトとの関係確認に必要なもの。
- 調査対象のうち、今後の動きが期待できないもの。

追跡対象外（`ignore`）:

- atprotoとの関連根拠がないもの。
- 独立した同一性や追加価値がないfork・ノイズで、再調査の必要もないもの。
- 利用者が明示的に追跡不要と判断したもの。

## 原則と責務境界

- 代表識別情報、分類、追跡状態、手動判断はローカルDBを正本とし、観測には根拠と確度を残す。未検証の外部情報・生成結果を確定情報として扱わず、手動判断を上書きしない。
- 発見では取りこぼしを減らし、同一性・所有関係・マージは保守的に扱う。補助情報の不足より、異なるprojectや人物の誤同一視を重大な誤りとする。
- 発見・調査・説明更新・候補判定と追加調査の要否判断を機械に任せ、機械判定を補うレビューを不要にすることを目指す。現行では不足や誤りを人が補い、紹介する対象や内容の最終選択は利用者が行う。
- 精度改善は既知例・同種例・別の例への退行を確認する。個別対象の特例やfallbackを蓄積せず、根拠・観測に基づく共通規則を修正する。
- 現在状態と判断に必要な履歴を保ち、生データは無制限に保存しない。履歴・根拠の保存は問題調査や再評価を支える設計であり、保存量そのものを成果としない。
- 現在の運用と情報の明確さを優先し、旧仕様・未使用インターフェースの後方互換は維持しない。
- 未決の公開directoryやapp record仕様に内部DBを先に合わせない。app lexicon完全互換を主目的にせず、不確かなmetadataで`app`を埋めない。

費用を第一の制約として、数十時間に及ぶ継続処理を運用できる構成を選びます。ローカルLLMはそのための現行手段であり、実行場所自体を目的としません。単発の呼び出しへ渡せる資料量、単件の待ち時間、並列化による全体時間を分けて評価します。

## 成功の判断

- 利用者が深掘りする価値を判断できるだけの背景と根拠を、候補とともに提示できる。
- 人力で新しいプロジェクトを探していた時に発見できたシードを継続的に取り込め、収集の失敗や不足を確認できる。
- atprotoの利用深度、サービスの利用可否、技術的新規性について、追加調査の起点となる情報を得られる。
- 曖昧な情報を確定情報と混同せず、利用者が判断を訂正できる。
- 調査に必要な利用者の時間、処理時間、失敗、保存量を観測し、継続可能な範囲に保てる。
- プロジェクト一覧を公開する場合、紹介用に蓄積した情報を作り直さずに利用できる。

具体的な目標値は、データ量、収集範囲、運用段階によって変わるため、このbriefでは固定しません。
