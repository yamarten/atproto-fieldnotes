# Promotion再発見導線の運用評価

Promotion再発見導線はhuman-reviewで了承され、実運用Webへ反映済みです。Lowered一覧の先行絞込みによる高速化は実装・検証済みですが、実運用には未反映です。通常一覧や他のviewの高速化と区別します。

## 次に行うこと

母艦で変更を統合・検証した後、実運用Webへの反映は別途承認を得て、実行中jobがないことを確認して行います。正本DBのmigration・補正は不要です。反映後はLowered一覧の実HTTP時間と、候補の検索・ページ送り・解除後の表示を確認します。実運用の再起動・正本への判断書込み・外部取得は今回の検証では行っていません。

2026-09-20の正本5,060件・候補1件の読み取り専用計測では、同じsnapshot内で旧全件経路と修正後を2組比較し、応答全体が一致しました。application内部は旧経路13.94 / 10.94秒、修正後5.76 / 2.28ミリ秒でした。これはHTTP・接続初期化を含まず、cacheを制御した統計的benchmarkでもありません。開発DBの実HTTPでは、架空候補2件（紹介済みを含む）の理由検索・ページ送りを1.65〜1.83ミリ秒で確認し、読込みでrevisionが変わらないことと解除の即時反映も確認しました。実データのAPI時間の代替にはしません。

初回の実運用反映で観測した21.8秒には、全projectの完全復元と重複正規化による既存負荷がありました。当時のI/O・競合・HTTP側の内訳は未確定です。Lowered以外のviewは従来の読込み経路を使うため、この既存負荷は残件です。再着手する場合は、同じrequest内の正規化・本体再読込み・baseline作成の重複を調べ、完全runtime viewとsnapshotの契約を保って比較します。

通常利用では、見慣れた候補の占有を解消できるか、確認済みの明示操作が負担にならないか、Lower priorityの理由検索で特集候補を回収できるかを評価します。明示操作が使われず占有が続く、情報不足の候補が依然上位に残る、理由検索では特集を組めない、のいずれかが分かった時は、[roadmapの紹介候補改善](../roadmap.md#atproto寄与度と紹介候補の順位)を再開します。

## 判断時の注意

品質scoreと受動的な非採用による減衰は変更していません。未見・根拠変化は有用性の保証ではなく、上位での長期非採用も未紹介全体を負例にする根拠ではありません。featuresの言い換えによる再提示と、未収集の変化の見逃しは残ります。現在値による紹介実績分析を過去時点の推薦精度とは扱いません。

現行の選択理由・契約は[評価仕様](../developer/specs/project-evaluation.md#紹介候補の表示順位保留)、保存形は[Project record](../developer/specs/project-record.md#promotionの確認記録)、操作は[Web UI](../user/web-ui.md#review)を参照してください。応答速度と評価の残件を解消したら、この文書とstatusからの参照を整理します。
