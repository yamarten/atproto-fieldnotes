# 機能説明とcollection定義の意味対応

2026-09-23。既存ローカルLLMで機能説明とschema説明を一組ずつ照合する方式は、通常調査への追加を不採用と判断しました。購読を注釈と同一視するなど、原文引用の検査では止められない意味の誤りが、一般規則の明確化後の未評価の組でも残りました。正しく対応する例もありますが、原文と定義の再確認を省ける品質ではありません。自動評価によって予備調査の負担を減らす目標は未達です。手動annotation追加を代替成果とせず、現行の材料表示・手動判断・順位規則を維持します。

これは今回の構成・入力・promptの採否であり、意味対応を使う全方式や他modelの不可能性を示す結果ではありません。2026-09-23に利用者が不採用判断と、文書の統合・一時実験ファイルの破棄を了承しました。正しい照合のメリットはあるものの、誤対応の検証負担と誤認リスクに対し、省力効果を確認できなかったという評価です。誤りが多数派だったことや、作業時間の純増を実測したという判断ではありません。

## 比較した問題と方式

人が機能とcollectionの関係を調べる時、現行UIは同じcollectionのscope、schema、record field、本文を並べます。本文の名前一致は示しますが、意味は判定しません。今回は「資料中のどの機能と、どの定義を照合するとよいか」を自動で絞れるかを評価しました。主機能の利用範囲を大きなpromptで総括する既却下方式、短文から操作を抽出する既却下方式は再実行していません。

初期案の「対応が明記／意味上関連／不明」は、実利用の主張と概念の近さを同じ軸へ混ぜやすいため、そのまま採用しませんでした。実験は一つの機能原文と一つのschema説明に限定し、次の暫定区分を使いました。この区分は製品の新しいfieldや仕様ではありません。

- `same_data`: 機能が扱う具体的なデータ概念と、定義の対象が直接対応する。
- `related`: 定義は周辺・補助データを表し、機能の内容そのものではない。
- `insufficient`: 別の内容、関係不明、schema説明の欠落、対象自身の機能がない。

出力は区分、機能側・schema側の連続原文引用、短い理由だけです。利用範囲、読書き操作、score、推薦は要求しません。未使用・将来予定でも同じデータ概念なら意味対応は成立し得ること、scopeは権限要求、recordは作成アプリ不明、schemaは定義であることを境界とします。今回の入力からscopeとrecord値は外し、以前の混同要因を減らしました。

v1の失敗後、同じ話題・保存形式だけでは同じデータにしないこと、主体・目的・粒度を保つこと、対応と現在の採用状態を分離することを一般規則として補ったv2を一度だけ試しました。project名・URL・fixture固有の例外はありません。

## 現行方式との差と処理費用

初回の実資料15組中、機能原文にcollection名があるのはrolldの1組でした。意味対応によって名前なしのGlean購読等を照合候補にできる一方、誤った候補も加わります。名前一致の少なさや候補数の増加を、推薦の有用性とみなしません。現行は全材料を人が照合する負担が残り、候補方式はその負担にLLM結果の検証が加わります。正しい例だけなら検索箇所を絞れますが、どの出力なら原文・schemaの再確認を省けるかを判別できませんでした。

## 採否と残る目標

今回のpromptを通常enrich、推薦順位、自動利用範囲判定へ接続しません。用途の近さは実利用の裏付けを増やさず、今回の実験では用途の近さ自体にも誤りが残りました。`same_data`を`main_data`へ、`related`を`supporting`へ置換することはできません。schemaだけの共有仕様も、動作中アプリと区別します。

Blueskyを対象とするか、読取り／書込みのどちらか、主機能との依存関係、技術的な学びは別の問いです。公開recordの読取りが主機能である場合もあり、repo scopeなしを非利用とせず、読取り中心を一律に減点しません。既存寄与度はschema・record等の観測に基づく値で、今回の意味対応でその責務を置き換えません。現行手動roleの責務整理は未実装のままです。

再検討には、少なくとも次が必要です。

- 機能と実際のcollectionアクセスをつなぐ、主体・対象・条件を確認できる原文または実装経路。scope・record存在・名称類似を代用しない。
- 今回の購読／注釈、本文／表示設定、処理／スコア、仕様／実装の反例を固定し、対応が欠ける例と実在対象の未使用確認例も含める。
- 正しい箇所を探す手間と、誤提案を訂正する手間を含む比較。人が省ける確認を示せず、annotation管理だけが増える方式を受理しない。

追加の実装取得やmodel変更はこの評価で実施しておらず、次の案件の優先度・着手順は母艦で判断します。同じpromptへの注意書き追加だけを無条件に反復する再開は推奨しません。
