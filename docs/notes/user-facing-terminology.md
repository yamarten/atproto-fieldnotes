# 利用者向け用語の編集方針

この文書は、README、`docs/brief.md`、`docs/user/`を編集する際の用語境界を残す作業用メモです。
利用者へ示す意味の正本は[利用ガイドの基本用語](../user/guide.md#基本用語)とし、この文書はコード・UI・開発文書との使い分けを定めます。

## 基本方針

- 利用者向け文書は、操作や判断を先に理解できる日本語を優先する。
- コマンド名、オプション、JSON field、enum、画面上の英語ラベルはバッククォート付きで原名を示す。
- 開発文書はコード検索と実装上の区別を優先し、内部用語を無理に訳さない。
- 同じ英語が複数階層で使われる場合は一括置換せず、対象を修飾する。

## 利用者向けの呼称

| 実装・画面上の語 | 利用者向けの呼称 | 境界 |
| --- | --- | --- |
| project | 登録プロジェクト | DBが1つの調査対象として保存する単位。一般的な外部プロジェクトは単に「プロジェクト」と書く。 |
| seed | シード | NSID、リポジトリURL、サービスURLを登録・特定の起点にする。 |
| enrich | `enrich` | 訳さず、登録プロジェクトを調査して現在情報と履歴を更新する処理と説明する。 |
| sync | 外部情報の取り込み | 双方向同期ではない。dry-runは「取り込み候補の確認」とする。コマンド名と`Sync`画面ラベルは維持する。 |
| investigation run | 調査実行記録 | 1登録プロジェクトの保存済み調査履歴に限定する。一括実行やバックグラウンドジョブには使わない。 |
| tracking state | 追跡状態 | 保存値`active`などは原名を併記する。 |
| review-queue | 要レビュー一覧 | 人による確認が必要な項目の一覧。review全般を固有概念にはしない。 |
| promotion-queue | 紹介候補一覧 | 「紹介候補レビュー」や「昇格候補」とは呼ばない。 |
| confirm | 採用 | 候補の識別子を登録プロジェクトに属するものとして認める操作。保存値`confirmed`を必要に応じて併記する。 |
| operator decision | 手動判断 | 採用、除外、保留、別プロジェクト指定など、自動判定より優先される判断。 |
| merge | マージ | マージ元、マージ先、マージ結果のプレビューと書き分ける。調査根拠のintegrationには使わない。 |

## 一括置換しないもの

- `project`は、project row、project dict、`projects` tableなど実装上の形を区別する必要がある。
- `run`は、調査実行記録、一括実行、収集処理、バックグラウンドジョブで単位が異なる。
- `confirmed`は、識別子・関係・根拠のclassificationや自動判定にも使われる。利用者操作の「採用」と完全な同義語にはしない。
- `classification`は識別子、関係、根拠で対象が異なる。対象を添えず「識別子分類」へ統一しない。
- `review`はqueue、signal、target、job、一般的な確認行為に使われる。利用者向け機能名だけを具体化する。
- `source`、`surface`、`family`、`current`、`bounded`、`guard`などは固定訳を増やさず、文脈に応じて具体的に説明する。

## Web UIとの関係

現行UIの`Projects`、`Review`、`Operations`、`Sync`などのラベルは、文書だけで改名したことにしません。
文書では正確なラベルを示したうえで、日本語の用途説明を添えます。画面内の説明を増やす場合も、長い説明はHelp導線へ寄せ、操作直近には誤操作を防ぐ短い補足だけを置きます。
