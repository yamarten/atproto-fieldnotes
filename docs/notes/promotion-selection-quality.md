# 紹介候補の選定品質：判断材料と残る課題

[TODOの紹介候補の順位改善](../developer/todo.md#atproto寄与度と紹介候補の順位)で、関心の高い共有Lexiconや特徴のある実装を取りこぼさず、選定時の不要な確認を減らす方式を判断するための比較資料です。保存済み候補の順位を変える案と、順位に使う分類・説明をLLMで再検証する案を評価しました。以下では同一DB snapshotによる順位比較と、限定した原文入力によるLLM比較を分け、採用を見送った理由と反例を残します。

2026-09-23の当時の配点による比較では、合計score順や種類別の枠配分が役立つ根拠を得られず、採用を見送りました。2026-10-23は、利用者との評価項目全体の見直しを受け、技術評価の別入口への分離と配点の整理を行いました。過去の配点の単純な並替えとは分けます。全体の捕捉率・ノイズ率や選定品質の合格を確認した結果ではありません。

自動再検証・修正・自己エスカレーションの追加も、限定的なモデル比較の後に利用者の打切り方針により当面保留です。モデル・取得資料・作業方式が実質的に変わり、以前の見逃しと利用負担を再評価できる場合に再開します。現行の候補条件は[評価仕様](../developer/specs/project-evaluation.md)、目標・再検討条件は[TODO](../developer/todo.md#atproto寄与度と紹介候補の順位)を参照してください。

現行の通常スコアはLexicon最大40・サービス最大20・活動最大30と、説明・採用済み公式repo各3点です。採用済みの所有NSIDを1件1点、うちDNS・PDSによる解決の有効な検証記録があるものを追加1点とし、20件の解決済み定義まで傾斜を持たせます。活動は3／7／14／30／60日以内で30／24／18／12／6点。サービスは公開画面20・ログイン入口16・入口確認済みの招待制12・要確認8点です。用途の文字列判別による後送り区分は、他サービス依存の評価へ置き換えられないため使いません。

配点の狙いは、Lexiconの具体的な定義と今見る理由を重視し、触りやすさ・調査の入口も小さく評価することです。説明はsummaryかtaglineのどちらかがあれば一度だけ3点で、2欄の重複や暫定解除には追加点を付けません。公式repoは採用済みかつ保留・除外中でないリンクに限り3点とし、候補URLだけでは加点しません。両補助点が揃っても6点、解決済み定義3件分です。サービスはbetaという呼称を不利にせず、観測範囲と招待制を一つの成分で扱います。入口確認は認証後の利用成功を証明せず、説明の存在は品質を、repoリンクは現在の到達性を証明しません。

confidenceの独立加点は不要と利用者が判断しました。レビュー推奨は資料が豊富で自動調査が読み切れない場合にも付くため、falseを紹介準備完了として加点しません。repo更新とcollection活動は意味が違いますが、両方の観測が揃う対象を過度に優遇しないため最新日時を一度だけ使います。活動日時は登場日時ではなく、速報性の評価は未解決です。

2026-10-23（JST）、同一の正本read-only snapshot・同一評価時刻で、直前の3成分案（ff3981bf）、サービス・補助点を改めて活動40点を維持する案、活動30点の現行案を比較しました。候補1,485件の集合と技術候補153件の順序は不変です。先頭10件の集合も不変で、現行順はStreamplace、Highport、Standard Reader、Orbyt、Bivri、Arbiter、Delve Feed、Gitosphere、Tangled、Delve Graph。先頭50件の活動加点ありは両40点案の49件から現行40件、所有Lexiconなしは6件から5件になりました。活動30点案は活動未観測・古い定義集も入りやすくしますが、これを選定品質の合格とは扱いません。解決済み20定義・公開画面・活動なしは60点、1定義・公開画面・3日以内活動は52点（両方とも補助点なし）で、新しさだけで大きな定義数差を逆転させません。活動40点案なら後者62点になります。

現行の先頭10件中8件はLexicon40点の上限に達し、9件は活動5日前の同点です。件数上限と観測日時の集中による順位の粗さが残ります。採用済みだが未解決の定義も基本点に入るため、上位にいることは解決済み公開や他サービスからの独立性の証明ではありません。サービス成分0点の上位には入口観測があっても採用済みservice URLがない対象があり、画面が利用不能という意味ではありません。個別対象に合わせた配点・帰属・category補正は行っていません。

配点を整理する前の実験では、Lexicon一律160点を400点にしても技術signalの優先段階を越えられませんでした。公開確認を最優先にするとSquireも160→8位となりましたが、これを利用者の「プロフィールだけなら低評価」という要件とは扱いません。解決済みに限定することや解決済みを重く評価することは許容され、現行は所有の基本点＋解決の追加点としました。集計は本文サンプル最大12件に依存せず、最新の失敗・型変更・発行元変更等を尊重する保存済み検証記録を使います。

同日の最初の3成分案（ff3981bf）と旧実装の比較では1,005→1,485候補となりました。技術だけの候補を技術入口へ分ける一方、解決検証を持たない採用済み定義やservice_status=noneの要確認serviceも残すため、母数が変わっています。この段階の通常順位はCalendar307→46位、Squire160→48位、Graze8→505位、Corgi9→362位、SkySweeper190→547位。Fortranskyとnucleusは通常候補を外れ、技術候補で引き続き確認できます。全上位の意味や帰属の正確さ、通常利用の省力効果は未測定です。この比較と、その後の上記配点調整はいずれも正本への書込み・外部取得・追加LLM推論を伴いません。

## 維持する判断

過去に利用者が確認した相対順は「共有Lexicon ＞ Juntos ＞ クライアント」です。焦点は特定プラットフォーム名ではなく、その背景にある他プロジェクトへの依存と独立性です。Blueskyクライアントは実害の代表例として扱い、名称だけの分類・自動除外や一律の後送りへ広げません。Juntos自体の特別な高優先や、技術的な学習価値と通常紹介の関心の同一視も意味しません。

未紹介stableを通常候補へ含め、stalledは既定から外す方針は実装済みです。Streamplaceは紹介済み扱いでもよい例外と確認され、未紹介対象の取りこぼしの代表例に数えません。

## 再開時に混同しない実装状態

旧入力構築の容量超過とrepository URL出力fieldの不一致は、後続実装で対応済みです。現行は整形空白削減と、claim・原文・参照先を一緒に扱うrepository解析縮約を行い、省略を記録します。旧失敗20件を未修正件数として引き継ぎません。根拠の省略による品質と実LLM生成は別途未検証です。

JuntosのLLM提案`live`は通常の最終処理で`unverified`へ戻りました。途中の`apply_llm_output`だけの加点を、通常enrichの最終保存不備と扱いません。一方、最終messageのないreasoning-only応答がJSON解析へ進んだ診断は別の確認対象として残ります。再開時に現行transportと照合します。

当時の比較入力・全出力は、このcheckoutには収録していません。本資料は比較結果と診断の要約で、完全な再実行の入口ではありません。既知例と上位・保存語彙に偏った比較なので、再開には現在の資料から対照を作り直し、未使用対象と通常導線での効果を確認します。新たな判別材料や具体的な運用問題がないまま、同じ例への配点・prompt調整を再開しません。
